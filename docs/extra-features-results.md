# extra_features: hand-given elements always in the synthesised pool

Date: 2026-09-16. Branch: `hyp/extra-features` (based on `hyp/combo`).

## Approach

`preset_features` replaces synthesis entirely, so it cannot express "synthesis plus a few
hand-given elements" -- H9 showed a small preset pool (`c_equal(on, on_G)` and its transitive
closure) makes blocks3ops solvable in principle, but that concept is never generated by
`generate_features` at any complexity on this build (H9/H10), so a synthesised-only pool can't
reach it either.

Added `extra_features` (`genfond/config/default.yaml`), the same shape as `preset_features`
(`booleans`/`numericals`/`concepts`/`roles` lists of DLPlan strings). When `preset_features` is
unset, `FeaturePool.__init__` (`genfond/feature_generator.py`) parses `extra_features` with the
factory and appends the parsed elements to the lists `generate_features` just returned --
*before* `self.features`/`self.concepts`/`self.roles` are built and before
`compute_uninformative_*`/`compute_redundant_*` run, so extras are pruned exactly like any
synthesised element and still carry DLPlan's own `compute_complexity()` for the `#minimize`.
Because they go through `factory.parse_*` directly rather than through `generate_features`,
they are exempt from the round's `max_complexity`/`concept_complexity_offset`/
`role_complexity_offset` limits -- confirmed by
`test_extra_features_concept_present_and_exempt_from_complexity_limit`, which shows a
complexity-3 extra concept absent from the pool at `max_complexity: 2` without `extra_features`
and present (with complexity 3) with it. Deduplicated against the synthesised lists (and against
each other) by string representation
(`test_extra_features_not_duplicated_when_also_synthesised`). If `preset_features` is also set,
`extra_features` is simply merged into the preset lists instead
(`test_extra_features_merged_with_preset_features`), since there is no generated pool to append
after.

Gates: `black`/`isort`/`mypy genfond tests`/`pytest` (207 passed, 1 pre-existing skip) all green
on the worktree.

## Validation run

One A/B on the workstation (desk-03), `--type datalog-sig -n 1 --max-memory 60000`, training set
`domain.pddl` + `p002-*`..`p007-*` + `p010-5` + `p017-5` (32 problems), `timeout 40m`,
`PYTHONHASHSEED=2`, config:

```yaml
seed: 2
add_problem_after_success: true
solve_time_limit: 300
role_complexity_offset: 2
concept_complexity_offset: 1
max_plans_per_problem: 8
planners:
  siw:
    restarts: 1
extra_features:              # omitted for the baseline run
  concepts:
    - c_all(r_transitive_reflexive_closure(r_primitive(on,0,1)),c_equal(r_primitive(on,0,1),r_primitive(on_g,0,1)))
    - c_not(c_all(r_transitive_reflexive_closure(r_primitive(on,0,1)),c_equal(r_primitive(on,0,1),r_primitive(on_g,0,1))))
  booleans:
    - b_empty(c_not(c_all(r_transitive_reflexive_closure(r_primitive(on,0,1)),c_equal(r_primitive(on,0,1),r_primitive(on_g,0,1)))))
```

Scored with `scripts/eval_policy.py --seed 0 -i 2` on the full 95-problem blocks3ops suite.

| run | solved/95 | rules | extra concept in final policy | training wall | eval wall |
|---|---|---|---|---|---|
| `extra_features` (extra.policy) | **26/95** | 63 | no | 40m3s (hit timeout) | 18.8s |
| baseline, no `extra_features` (baseline.policy) | **91/95** | 7 | n/a | 40m12s (hit timeout) | 58.5s |

Both training runs hit the 40-minute cap and returned via the graceful SIGTERM stop (the "best
policy seen across the run" mechanism, `3d757ec`), not a normal convergence.

**The extra concept was reachable and used mid-run.** Grepping the training log confirms
candidate policies around minutes 15-20 of the `extra_features` run selected rules built on
`c_all(r_transitive_reflexive_closure(r_primitive(on,0,1)),c_equal(...))` (218 matching lines
across several candidate "Final policy" dumps before the run's actual end) -- the mechanism does
make the concept available and selectable, as intended and as the unit tests check in isolation.
But the policy frozen as *best* when the wall clock ran out was a later, worse one: 63 rules,
solving only 26/95, with **no** occurrence of the extra concept (confirmed both by grepping the
training log's final "Final policy: 63 rules" dump and by `print_policy.py` on the pickled
`extra.policy`). The baseline run, with a strictly smaller pool and nothing to append, converged
on a clean 7-rule policy that solves 91/95 -- matching the quality of the best `datalog-sig`
policies seen elsewhere in this log (e.g. the "91/95 run" noted in the training log referenced
from `MEMORY.md`).

**Reading, not fixing.** This is a single seeded run, and `add_problem_after_success` +
`frontier_expansion` make the round trajectory sensitive to exactly how much wall time each
round takes -- adding always-available elements (here 3 extra concepts/booleans across every
round, on top of whatever `generate_features` produces at each complexity) changes grounding and
solve time for every round of the whole run, not just the round where they'd help. That shifted
the run onto a different, worse trajectory inside the same 40-minute budget: more rounds spent
exploring policies built from the larger pool, ending on a 63-rule overfit policy instead of
converging to something small. The code change itself is confirmed correct in isolation (pool
membership, complexity exemption, dedup, pruning -- all unit-tested); this run does not show
`extra_features` improving blocks3ops end-to-end, and a fair comparison would need a wall-time
budget large enough for both configurations to converge, or several seeds. Not rerun further per
the "report, don't fix" policy for research-code validation runs.
